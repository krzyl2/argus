# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Phase Type: New Screens, Existing Design System

This phase adds genuinely new screens (group list, group editor, algorithm chooser, guided flow,
area-grouped sensor browse, ranked attribution display) on top of the Phase 7 Preact+Vite SPA. It does
**NOT** introduce a new design system. `argus.css` (`orchestrator/ui/public/css/argus.css`) — the same
token set carried forward from Phase 7 — remains the single visual source of truth. No new colors,
spacing values, font sizes, weights, or component patterns beyond what that file already declares.

Stack is locked (Phase 7, not re-litigated): Preact + Vite + TypeScript, hand-rolled hash router
(`router.ts`), `@preact/signals` state, relative-fetch API client (`api/client.ts`, no leading slash),
Vitest + @testing-library/preact. shadcn is not applicable (Preact, not React/Next; `argus.css` is the
locked styling decision) — shadcn init is skipped exactly as in Phase 7.

The user is function-first: no unsolicited animation/polish. Everything below optimizes for correct,
transparent interaction contracts (this is the actual design crux — ALGO-01..04 transparency
requirements), not visual flourish.

## Preset + Advanced Interaction Contract (ALGO-01, ALGO-02)

This is the transparency crux of the phase. Contract, not suggestion:

1. **Default state:** `SensitivityPresetPicker` shows exactly 3 options — Low / Med / High — as a
   radio group (native `<input type="radio">`, `accent-color: var(--color-accent)`, same pattern as
   the existing tracked-checkbox). Med is the default selection for a newly-added detector. Raw
   parameter values are NOT visible in this state.
2. **Preset → params expansion:** Selecting a preset immediately (client-side, no round-trip) expands
   to concrete param values sourced from `GET /api/detectors/catalog` (per CONTEXT.md — catalog is
   the single source of truth for preset→param mapping). The expanded values are what gets written to
   `GroupConfig.Params` on save — self-contained YAML, no runtime preset lookup needed at score time.
3. **Advanced toggle:** A `<details>`/`<summary>` disclosure (`AdvancedParamsDisclosure`, same visual
   pattern as `DetectorDisclosure`) labeled "Advanced — view/override parameters". Expanding it reveals
   the exact param grid (field per param, types/ranges from the catalog's schema) pre-filled with the
   currently-expanded preset values.
4. **Override semantics:** Editing any field in the Advanced grid overrides that specific value while
   leaving the others at the preset's expansion. The preset radio selection itself is NOT cleared by an
   override (the label "Med, customized" — see Copywriting Contract — communicates the divergence,
   rather than silently reverting to an unlabeled custom state).
5. **Never hide the override from the operator:** once any field is overridden, a visible inline note
   appears next to the preset radio group (not just inside the collapsed disclosure) so closing
   Advanced doesn't hide the fact that raw values differ from the plain preset. This is the
   non-negotiable transparency requirement from CONTEXT.md/ALGO-01..04.

## Guided Flow Contract (ALGO-04)

1. `AlgorithmChooser` opens in **guided mode** by default for a new detector assignment, with a manual
   "Skip — choose manually" link/button always visible (never forces the guided path).
2. `GuidedFlowStep` asks one question: **"What are you monitoring?"** with exactly 2 answers per
   CONTEXT.md:
   - "A room/area's related sensors, together" → pre-selects joint-multivariate / ECOD
   - "Which one sensor diverges from its peers" → pre-selects peer-divergence
3. **Immediately after an answer**, the picked `AlgorithmCard` is shown pre-selected AND visibly
   marked as guided-recommended (a label, e.g. "Suggested based on your answer" — see Copywriting
   Contract — not merely a color difference, since color alone is not accessible/transparent enough).
   The full `AlgorithmCard` grid remains visible and clickable below/beside it — **one click on any
   other card overrides the guided pick with zero friction** (no confirmation dialog to override; this
   is a low-stakes, pre-save, reversible-by-not-saving choice, same class of action as Phase 7's
   "Remove detector").
4. **Never** auto-apply the guided pick without this visible intermediate state — an opaque "we chose
   X for you" with no way to see the alternatives is explicitly out of scope
   (REQUIREMENTS.md Out-of-Scope: "Fully automatic algorithm selection").
5. Each `AlgorithmCard` (guided or manual mode) always shows its "best for…" description (ALGO-03),
   sourced from `GET /api/detectors/catalog` — never hardcoded client-side copy that could drift from
   the catalog.

## Attribution Display Contract (GRP-09)

1. `AttributionPanel` appears only on the `#/groups/:id` edit screen (existing groups only — a new,
   unsaved group has no verdict yet).
2. **Has contributions (ECOD/COPOD):** renders a ranked list of `AttributionBar` rows, sorted
   descending by `contribution` value (already ranked server-side per the proto `FeatureContribution`
   list — the SPA does not re-sort against a different key). Bar width is contribution value normalized
   to the top contributor = 100% (relative ranking visual, not an absolute 0-1 scale claim). Top-ranked
   row uses `--color-accent` fill; all other rows use `--color-element`-on-`--color-surface` neutral
   fill (not accent) — accent is reserved for "the one answer", consistent with the Color contract's
   accent-reservation rule.
3. **No attribution (PCA/IForest):** renders a single line of `--color-text-secondary` body text:
   *"This algorithm does not provide per-feature attribution."* This is NOT an error state — no
   `--color-status-error`, no error icon/banner. It is a factual, honest capability statement (per
   CONTEXT.md: "PCA/IForest honestly show 'no per-feature attribution'", never a fabricated ranking).
4. **No verdict yet:** renders `EmptyState`-style copy: *"No anomaly score yet — attribution will
   appear after the next batch run."*
5. **Refresh:** the panel polls `GET /api/groups/{id}/status` on an interval while the edit screen is
   open (per CONTEXT.md: "roughly the batch interval cadence", no SSE). Poll stops on route change
   away from `#/groups/:id` (clear the interval on unmount, same discipline as `SensorSearchInput`'s
   debounce-timer cleanup-on-unmount).

## Sensor Search & Browse Contract (SRCH-01, SRCH-02, SRCH-03)

1. **Search (SRCH-01):** `SensorSearchInput`'s match predicate covers `friendly_name` (case-insensitive
   substring) OR `entity_id` — a strict superset of Phase 7 behavior, zero regression on entity_id
   search. Placeholder copy updates from "Filter by entity ID…" to "Filter by name or entity ID…"
   (this placeholder change applies everywhere `SensorSearchInput` is used, including `#/sensors` —
   consistent product behavior, not a per-screen fork).
2. **Browse (SRCH-02):** `SensorList`'s area-grouping mode renders one collapsible `<details>` section
   per HA area name (alphabetically sorted), with a final "Ungrouped" or per-domain fallback section
   for sensors with no resolved area. Each section header reuses `.argus-disclosure-toggle` styling
   and shows a count, e.g. "Living Room (4)".
3. **Suggestions (SRCH-03):** `AreaSuggestionBanner` on `#/groups` surfaces "N sensors share area
   {area} — group them?" for areas with ≥3 untracked-in-any-group sensors (mirrors the min-member
   floor of 3). Clicking it navigates to `#/groups/new` with the member picker pre-filled (not
   pre-saved) with that area's sensors — operator still reviews, edits mode/algorithm, and explicitly
   saves. Dismissing the banner (a small "×" or "Not now" link, `.argus-label` size) hides that
   specific suggestion for the session; it is not persisted server-side (no new config surface for
   dismissal state — out of scope, keep this lightweight).

| State | Trigger | UI | Copy |
|---|---|---|---|
| Editing | default | Form fields active, save button enabled if valid | n/a |
| Below member floor | <3 members selected | `FieldValidationError` under member picker | "A group needs at least 3 members." |
| Unit mismatch (peer mode only) | peer_divergence mode + members with differing `unit_of_measurement` | `FieldValidationError` under member picker | "Peer-divergence groups need members with the same unit. Found: {units}." |

## API Contract (informative — planner/executor finalize exact schema)

Per `08-CONTEXT.md` (locked): all endpoints go through `IsAuthorizedRequest` first, matching the Phase 7
auth pattern exactly. All SPA calls use `apiGet`/`apiPost` (relative paths, no leading slash).

| Endpoint | Method | Purpose |
|---|---|---|
| `api/groups` | GET | List all groups from live config — backs `#/groups` |
| `api/groups/save` | POST | Write the `groups:` list to `entities.yaml` via `ConfigWriter` + `LiveEntitiesConfig.Swap` (hot-reload, no restart) — backs group editor save |
| `api/detectors/catalog` | GET | Per group-detector: Low/Med/High preset→param mapping, "best for…" description, param schema (types/ranges for Advanced form) — single source of truth for `AlgorithmCard` + `SensitivityPresetPicker` + `AdvancedParamsDisclosure` |
| `api/groups/{id}/status` | GET | Last verdict + ranked `FeatureContribution` list (or empty/null for non-attributable detectors) for `AttributionPanel` polling |

## Explicit Non-Goals (guardrails against scope creep)

- No new color tokens, spacing tokens, font sizes, or weights beyond `argus.css`'s existing set.
- No icon library or chart library — attribution bars are plain CSS `div` width, not a charting dependency.
- No continuous sensitivity slider (Out-of-Scope, REQUIREMENTS.md) — Low/Med/High + Advanced only.
- No opaque/automatic algorithm selection without a visible, overridable guided-pick state.
- No fabricated attribution ranking for PCA/IForest — honest "not supported" message only.
- No auto-grouping — `AreaSuggestionBanner` is always operator-approved, never auto-applied.
- No custom HA dashboards — attribution display is read-only inside the Argus SPA only (PROJECT.md exclusion).
- No new animation/transition beyond what `argus.css` already declares (`.argus-spin`, opacity
  transitions, disclosure arrow rotation) — reuse, do not add.
- No regression to `#/sensors` — that screen and its components are untouched except the shared
  `SensorSearchInput` placeholder/predicate extension, which is additive (entity_id matching still works).
