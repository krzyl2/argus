<objective>
Half B (Python detector layer). Add a pairwise-delta scoring path for 2-member `peer_divergence`
groups: compute `member_a - member_b`, and score/fit that derived univariate signal with the
existing production-proven PyOD MAD detector. Route to it from the servicer purely on
`len(request.series) == 2`, leaving `PeerDivergenceDetector`'s classic N>=3 contract completely
untouched.

Purpose: Deliver GRP-11's detection capability — reuse proven univariate anomaly detection on a
meaningful derived signal rather than inventing new group math (ROADMAP scope item 2).
Output: New `PairwiseDeltaDetector` class + new `pairwise_delta.py`, a new `PyODDetector.is_anomaly()`
accessor, servicer 2-member sub-branches in `ScoreGroupBatch`/`FitGroup`, and unit tests. No proto
changes, no new packages, no ModelStore changes.
</objective>

<assumptions>
- **[ASSUMED, low-risk] 2-member peer_divergence returns ONE group-level verdict** (empty
  `per_member`, empty `contributions`) — RESEARCH.md Assumption A2 / Open Design Question #5. The
  pairwise delta cannot attribute the anomaly to either member (same degeneracy the classic N=2 case
  has), so contributions are deliberately left empty — never fabricate them. The .NET side (Plan
  09-03) reacts to this response shape. Operator-revisable; flip by populating `per_member` here and
  the count-aware helper in 09-03.
- **[CONSTRAINT — must keep passing UNMODIFIED]**
  `detector/tests/test_peer_divergence.py::TestPeerDivergenceFloor::test_below_floor_returns_no_verdict`
  asserts `PeerDivergenceDetector.score_batch` errors on exactly 2 members. This is why the new
  logic lives in a NEW class selected by the servicer on member count — NOT inside
  `PeerDivergenceDetector`. Do not edit `peer_divergence.py` or this test.
</assumptions>
